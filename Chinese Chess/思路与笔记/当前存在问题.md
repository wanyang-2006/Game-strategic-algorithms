## 1. 会直接导致编译失败的问题(解决)

### 1.1 `getchessbook()` 定义过早，使用了不完整类型

约 L99-L158：

```cpp
class Chess;
class Move;
bool getchessbook(Chess& chess,Move& bookMove){
    ...
    uint64_t tmpkey = chess.getZobristKey();
    ...
    Move res(...);
    ...
    if(!chess.isMoveValidWithForbidden(res)){
```

这里只是前向声明了 `Chess` 和 `Move`，但马上调用了 `Chess` 的成员函数，并构造 `Move` 对象。 **不完整类型不能调用成员函数，也不能实例化对象** 。这在标准 C++ 中会编译失败。

修复方式：保留函数声明，把函数定义移动到 `Chess`、`Move` 完整定义之后：

```cpp
class Chess;
struct Move;

bool getchessbook(Chess& chess, Move& bookMove);

// 等 Chess 和 Move 都完整定义后，再写函数体
bool getchessbook(Chess& chess, Move& bookMove) {
    ...
}
```

## 2. 最严重的运行逻辑错误：`isQuietMove()` 下棋后不回撤(解决)

约 L2916-L2919、L3047-L3050：

```cpp
for(auto& node : tmpMoveNodes){
    bool isQuiet = this->isQuietMove(board->state[board->currTurnId],node);
    {
        MoveGuard guard(this, node);
        ...
    }
}
```

而 `isQuietMove()` 是：

```cpp
bool ChessAI::isQuietMove(vector<Grid>& tmpgrid,MoveNode& tmpmove){
    MoveNodeFront(tmpmove);
    this->evaluator.getGridcontrol();
    return havethreat(board->state[board->currTurnId],board->currColor);
}
```

这是全程序最危险的问题。`isQuietMove()` 调用了：

```cpp
MoveNodeFront(tmpmove);
```

也就是执行了一步棋，但 **没有调用 `MoveNodeBack()` 或 `undoMove()` 回撤** 。

随后外层又立刻执行：

```cpp
MoveGuard guard(this, node);
```

这等于同一个 `node` 被执行了两次。第一次执行后 `currColor` 已经切换，源格也可能已经变空；第二次执行同一招时：

```cpp
assert(sourceGrid.color == currColor);
```

在 Debug 下大概率断言失败；在 Release 下如果断言被禁用，则会把空格移动到目标格，甚至把刚刚移动的棋子抹掉。

更严重的是：`ChessAI AI(&chess)` 直接操作外部 `chess`，所以搜索过程中一旦 `isQuietMove()` 泄漏了一步， **主棋盘也会被污染** 。之后即使 AI 超时 fallback 到随机走子，随机走子也是基于已经损坏的棋盘生成的。

应立即改成 RAII 回撤：

```cpp
bool ChessAI::isQuietMove(vector<Grid>&, MoveNode& tmpmove) {
    MoveGuard guard(this, tmpmove);

    // 这里判断：是否吃子、是否将军、是否造成威胁等
    bool givesCheck = false; // 需要按实际规则计算
    bool capture = false;    // 可从移动前状态判断
    bool threatened = havethreat(board->state[board->currTurnId], board->currColor);

    return !capture && !givesCheck && !threatened;
}
```

而且当前返回值语义也反了：函数名叫 `isQuietMove`，但它返回的是 `havethreat(...)`，即“有威胁”。这会导致 LMR、杀手着法等启发式全部误判。

## 3. 空步裁剪 `MoveNodeVoid()` 是非法实现，会删棋或断言失败(解决)

约 L2618-L2625：

```cpp
void ChessAI::MoveNodeVoid(){
    Move tmpmove;
    tmpmove.source_x = 1;
    tmpmove.source_y = 1;
    tmpmove.target_x = 1;
    tmpmove.target_y = 1;
    board->makeMoveAssumeLegal(tmpmove);
}
```

这是把 `(1,1)` 到 `(1,1)` 当成“空步”。但 `makeMoveAssumeLegal()` 假设走法合法，并且会执行：

```cpp
auto &sourceGrid = state[currTurnId][xy2pos(move.source_x, move.source_y)];
auto &targetGrid = state[currTurnId][xy2pos(move.target_x, move.target_y)];
...
targetGrid.type = sourceGrid.type;
targetGrid.color = sourceGrid.color;
assert(sourceGrid.color == currColor);
sourceGrid.color = EMPTY;
sourceGrid.type = None;
```

当 source 和 target 是同一个格子时，`sourceGrid` 和 `targetGrid` 是同一个引用。结果是：

1. 如果 `(1,1)` 是空格，Debug 下断言失败。
2. 如果 `(1,1)` 恰好有当前方棋子，Release 下会把该棋子清空。
3. 这不是空步，而是“伪装成空步的非法落子”。

应单独实现空步，不要复用 `makeMoveAssumeLegal()`：

```cpp
void Chess::makeNullMove() {
    state.push_back(state[currTurnId]);
    currTurnId++;
    continuePeaceTurn.push_back(continuePeaceTurn[currTurnId - 1] + 1);
    lastMoveEaten.push_back(false);
    currColor = oppColor();
}

void Chess::undoNullMove() {
    undoMove();
}
```

并用 RAII 包住，防止搜索超时时没有回撤。

## 4. 搜索异常会导致棋盘栈未回撤（解决）

在 `alpha_beta_search()` 和 `alpha_beta_PVS_search()` 中，空步裁剪写法是：

```cpp
this->MoveNodeVoid();
int null_val = -alpha_beta_PVS_search(...);
this->board->undoMove();
```

如果递归搜索中抛出 `TimeOutException`，`undoMove()` 不会执行。虽然根节点捕获了异常，但棋盘已经多压了一层状态，`currTurnId`、`currColor`、`state` 全部错位。

应使用 RAII：

```cpp
struct NullMoveGuard {
    ChessAI* ai;
    NullMoveGuard(ChessAI* a) : ai(a) { ai->board->makeNullMove(); }
    ~NullMoveGuard() { ai->board->undoMove(); }
};
```

然后：

```cpp
{
    NullMoveGuard guard(this);
    int null_val = -alpha_beta_PVS_search(...);
}
```

你已经为普通走子写了 `MoveGuard`，空步也必须同样处理。

## 5. `getWin()` 的胜负符号是反的

约 L2646-L2653：

```cpp
bool ChessAI::getWin(){
    auto& tmpstate = this->board->state[board->currTurnId];
    for(auto& s : tmpstate){
        if(s.color == board->currColor && s.type == King){
            return false;
        }
    }
    return true;
}
```

在 negamax 中，进入子节点后 `currColor` 已切换为对手。如果对手的王被吃掉，`getWin()` 返回 true。随后搜索函数返回：

```cpp
return 999999;
```

但是上一层会取负：

```cpp
score = -alpha_beta_PVS_search(...);
```

于是“我吃掉对方将帅”反而得到 `-999999`，变成最差招法。

正确做法：如果当前行动方已经没有王，说明当前行动方输，应返回极小值，而不是极大值：

```cpp
if (sideToMoveKingMissing()) {
    return minstateval + plyPenalty;
}
```

或者不要允许“吃将帅”进入普通搜索树，而是用“无合法应将”作为胜负判定。

## 6. `getGridcontrol()` / `havecontrol` 存在未初始化和越界访问

### 6.1 `havecontrol[90]` 从未初始化，也没有在每次计算前清空

约 L393：

```cpp
bool havecontrol[90];
```

构造函数：

```cpp
EvalRecord() : board(nullptr), isKingattacked(false) {}
```

没有初始化 `havecontrol`。`getGridcontrol()` 只清空了：

```cpp
GridControl[side][pos] = 0;
```

却没有：

```cpp
havecontrol[pos] = false;
```

之后 `hasattackchance()` 直接读：

```cpp
return this->havecontrol[board->xy2pos(mx,my)];
```

这会读未初始化 bool，属于未定义行为。即使第一次碰巧正常，后续评估也会被上一次的 true 残留污染。

应在构造函数和 `getGridcontrol()` 开头清空：

```cpp
EvalRecord() : board(nullptr), isKingattacked(false) {
    std::fill(&GridControl[0][0], &GridControl[0][0] + 2 * 90, 0);
    std::fill(havecontrol, havecontrol + 90, false);
}
```

并在每次 `getGridcontrol()` 里也清空 `havecontrol`。

### 6.2 兵卒横向控制可能访问棋盘外

约 L2030-L2038：

```cpp
tx = x + dx_lr[dir], ty = y;
if(board->inBoard(tx, ty)){
    GridControl[colorId][board->xy2pos(tx, ty)] ++;
}
if(curGrid.color == board->oppColor() && board->state[tmp][board->xy2pos(tx,ty)].type != None){
    this->havecontrol[board->xy2pos(x,y)] = true;
}
```

第二个 `if` 不在 `inBoard()` 内部。当兵在 `x = 0` 时，`tx = -1`；当兵在 `x = 8` 时，`tx = 9`。这会调用：

```cpp
xy2pos(-1, y)
xy2pos(9, y)
```

然后访问 `vector` 越界，属于严重内存安全问题。

应改成：

```cpp
if (board->inBoard(tx, ty)) {
    int pos = board->xy2pos(tx, ty);
    GridControl[colorId][pos]++;
    if (curGrid.color == board->oppColor() &&
        board->state[tmp][pos].type != None) {
        havecontrol[board->xy2pos(x, y)] = true;
    }
}
```

## 7. `calstate()` 没有保证控制表是当前局面的

`calstate()` 调用：

```cpp
res += this->calstaticstate(target,color);
res += this->caldynamicstate(target,color);
```

但没有先调用：

```cpp
getGridcontrol();
```

而 `calstaticstate()` 会用：

```cpp
hasattackchance(x, y)
```

```cpp
GridControl[idx][pos]
```

因此评估函数依赖的是上一次残留的控制表，甚至是未初始化控制表。唯一明显调用 `getGridcontrol()` 的地方是错误的 `isQuietMove()`。这会导致局面评估完全不稳定。

建议：

```cpp
int EvalRecord::calstate(vector<Grid>& target, colorType color) {
    // 如果 target 就是 board->state[currTurnId]，可以先更新
    getGridcontrol();

    int res = 0;
    ...
}
```

更好的设计是让 `getGridcontrol(target)` 接收局面参数，而不是偷偷读取 `board->state[currTurnId]`。

## 8. `calShapePenalty()` 使用了错误的红黑底线

约 L2476-L2484：

```cpp
int kingY = (color == RED) ? 9 : 0;
int centerM_Y = (color == RED) ? 8 : 1;
```

但 `resetBoard()` 中红方在 `y = 0`，黑方在 `y = 9`：


所以 `calShapePenalty(RED)` 会去看 `(4,9)`，那里是黑将；`calShapePenalty(BLACK)` 会去看 `(4,0)`，那里是红帅。结果通常直接：

或者统一整份代码的坐标系。目前 `baseLine[2] = {9, 0}`、`resetBoard()`、`inKingArea()`、兵卒前进方向、评估表翻转逻辑之间存在坐标语义混乱。

## 9. `Chess::isattacked()` 的 King 判断明显写错

约 L1515：

```cpp
if ((abs(dex) == 1 && abs(dey) == 0 && inKingArea(mx, my, oppColor(currColor))) ||
    (abs(dex) == 0 && abs(dey) == 1 && abs(dey) == 0 && inKingArea(mx, my, oppColor(currColor))))
```

第二个分支同时要求：

```cpp
abs(dey) == 1 && abs(dey) == 0
```

永远不可能成立。也就是说这里的“将帅纵向相邻攻击”永远检测不到。

而且 `inKingArea(mx, my, oppColor(currColor))` 依赖当前行动方 `currColor`，不是依赖攻击棋子的颜色 `color`。判断某个 `color` 的将帅能否攻击一个格子时，应该判断目标格是否在该将帅自己的九宫内：

```cpp
inKingArea(mx, my, color)
```

更合理写法：

```cpp
if (abs(dex) + abs(dey) == 1 && inKingArea(mx, my, color)) {
    return true;
}
```

## 11. `alpha_beta_PVS_search()` 中 LMR 结果被覆盖

约 L2925-L2939：

```cpp
if(depth >= 3 && moveIndex && isQuiet){
    int R = 1;
    val = -alpha_beta_PVS_search(depth - 1 - R, -alpha - 1,-alpha);

    if(val > alpha){
```

## 12. 开局库选择最高频走法的逻辑是错的

约 L133-L141：

```cpp
int selectIdx = 0;
vector<int> selectIdxes;
selectIdxes.push_back(selectIdx);
for(int i = 1;i < moves.size();i ++){
    int c = moves[i].get("count",0).asInt();
    if(c > selectIdxes[0]){    
        selectIdxes.clear();
    }
    selectIdxes.push_back(i);
}
```

`selectIdxes[0]` 是“走法索引”，不是“最大 count”。这里在拿频次 `c` 和索引比较，逻辑完全错误。而且无论是否清空，最后都会 `push_back(i)`，不会真正只保留最大频次组。

应改成：

```cpp
int bestCount = moves[0].get("count", 0).asInt();
vector<int> selectIdxes{0};

for (int i = 1; i < moves.size(); ++i) {
    int c = moves[i].get("count", 0).asInt();
    if (c > bestCount) {
        bestCount = c;
        selectIdxes.clear();
        selectIdxes.push_back(i);
    } else if (c == bestCount) {
        selectIdxes.push_back(i);
    }
}
```

## 13. `makeMoveAssumeLegal()` 对非法输入没有防御，且断言位置太晚

约 L1005-L1030：

```cpp
auto &sourceGrid = state[currTurnId][xy2pos(move.source_x, move.source_y)];
auto &targetGrid = state[currTurnId][xy2pos(move.target_x, move.target_y)];
...
targetGrid.type = sourceGrid.type;
targetGrid.color = sourceGrid.color;
assert(sourceGrid.color == currColor);
sourceGrid.color = EMPTY;
sourceGrid.type = None;
```

问题：

1. 没有检查 `source_x/source_y/target_x/target_y` 是否在棋盘内。
2. 没有检查源格是否真的是当前方棋子。
3. `assert(sourceGrid.color == currColor)` 放在修改 target 之后；Debug 下断言失败时对象已经被部分修改。
4. Release 下断言被移除，非法移动会继续执行。

应改成：

```cpp
bool Chess::makeMoveAssumeLegal(const Move& move) {
    if (!inBoard(move.source_x, move.source_y) ||
        !inBoard(move.target_x, move.target_y)) {
        throw std::out_of_range("move out of board");
    }

    const Grid& src0 = state[currTurnId][xy2pos(move.source_x, move.source_y)];
    if (src0.color != currColor || src0.type == None) {
        throw std::logic_error("source is not current side piece");
    }

    ...
}
```

真正用于搜索的高性能版本可以保留“假设合法”，但必须保证所有调用方都不会传非法 move。现在 `MoveNodeVoid()` 已经违反了这个前提。

## 16. 置换表没有有效位，`zobrist_key == 0` 有误命中风险

约 L284-L294：

```cpp
struct TTStateNode{
    uint64_t zobrist_key;
    int depth;
    int score;
    HashFlag flag;
    Move best_move;
};

TTStateNode HashTable[TT_SIZE];
```

全局数组会零初始化，所以空表项的 `zobrist_key == 0`、`depth == 0`、`flag == EXACT`。如果某个真实局面 Zobrist key 恰好为 0，或者未来某些初始化变动导致 key 为 0，就会误命中空表项。

应增加：

```cpp
bool valid;
```

或初始化为不可能的 sentinel，并在 `probeHash()` 先判断 `valid`。

另外，置换表 key 只包含棋盘和行动方，没有包含：

1. 重复局面历史。
2. `continuePeaceTurn`。
3. 禁手相关历史。

但你的合法走法受 `repeatAfterMove()` 影响，所以相同棋盘在不同历史下合法性可能不同。TT 复用会有规则层面的错误风险。

## 17. `repeatAfterMove()` 过度简化了中国象棋禁手规则

约 L1380-L1410：

```cpp
return repeatTime >= 3;
```

当前实现是：只要非吃子历史中同方重复同一局面达到 3 次，就禁止。中国象棋实际要区分长将、长捉、一将一闲、双方循环等，不能简单禁止所有三次重复。这个实现会误判很多允许/不允许的循环局面。

如果只是比赛平台接受“简化三次重复”，可以保留；如果目标是真正规则，这里需要重写。

## 18. `ChessAI` 原始指针所有权存在拷贝安全隐患

约 L418-L419、L1649-L1671：

```cpp
Chess *board;
bool ownBoard;
...
ChessAI::ChessAI(): board(new Chess()),ownBoard(true),searchTime(900) { ... }
...
ChessAI::~ChessAI(){
    if(ownBoard && board != nullptr){
        delete board;
    }
}
```

当前类没有自定义拷贝构造、拷贝赋值、移动构造、移动赋值。默认拷贝会复制：

```cpp
board
ownBoard
evaluator.board
```

如果一个 `ownBoard == true` 的 `ChessAI` 被拷贝，就会出现两个对象都认为自己拥有同一块 `Chess*`，析构时 double delete。

建议至少禁用拷贝：

```cpp
ChessAI(const ChessAI&) = delete;
ChessAI& operator=(const ChessAI&) = delete;
```

更好的方式是：

```cpp
std::unique_ptr<Chess> ownedBoard;
Chess* board;
```

或者直接不要在 `ChessAI` 内部拥有棋盘，由外部统一管理。

## 19. `EvalRecord` 保存裸指针，容易悬空

约 L388-L389：

```cpp
Chess *board;
void copyBoard(Chess *currentBoard) { board = currentBoard; }
```

这个函数名叫 `copyBoard`，但实际上只是浅拷贝指针，不复制棋盘。`EvalRecord` 不拥有这个对象。如果外部 `Chess` 生命周期结束，`EvalRecord::board` 就悬空。

建议改名并加约束：

```cpp
void bindBoard(Chess& currentBoard) { board = &currentBoard; }
```

或者让 `EvalRecord` 不保存指针，每次评估时显式传入 `Chess&`。

## 20. `getcurstones()` 没有清空缓存

约 L1481-L1492：

```cpp
evaluator.curstones.push_back(...);
evaluator.curattacked.push_back(...);
```

函数开始没有：

```cpp
clear()
```

多次调用会把旧局面的棋子、受攻状态不断累积，导致数据失真。

应加：

```cpp
evaluator.curstones.clear();
evaluator.curattacked.clear();
```

## 21. `calShapePenalty()` 使用 `board->betweenNotEmptyNum()`，但传入的是 `target`

约 L2499-L2500：

```cpp
int blockCount = board->betweenNotEmptyNum(4, y, 4, kingY);
```

`calShapePenalty(vector<Grid>& target, ...)` 名义上评估的是 `target`，但 `betweenNotEmptyNum()` 读取的是：

```cpp
board->state[board->currTurnId]
```

如果 `target` 不是当前真实棋盘，而是一个假想局面或拷贝局面，阻挡数就算错。类似问题在评估函数里多次出现：参数是 `target`，实际却通过 `board` 读当前状态。

建议把这类工具函数改成可以接收局面：

```cpp
int betweenNotEmptyNum(const vector<Grid>& st, int sx, int sy, int ex, int ey);
```

## 22. `generateMoves()` 中反复 `makeMove/undoMove`，复杂度和状态风险很高

当前每生成一个候选走法，就调用：

```cpp
isMyKingAttackedAfterMove(Move(...))
```

而这个函数会：

```cpp
makeMoveAssumeLegal(move);
...
undoMove();
```

也就是每个候选都复制整个 90 格局面，压入 `state`，再弹出。搜索里又频繁生成走法，这会非常慢，而且只要任意路径异常没有回撤，整个棋盘状态就错乱。

建议长期改成增量 make/unmake：

```cpp
struct UndoInfo {
    Move move;
    Grid captured;
    int prevPeace;
    bool prevEaten;
};
```

走子时只修改两个格子，回撤时用 `UndoInfo` 恢复，不要每步复制全盘。

## 23. `alpha_beta_select()` 中排序前没有给根节点真正估值

约 L2675-L2679：

```cpp
newMoveNode.value = alpha;
selected.push_back(newMoveNode);
...
MoveNodesort(selected);
```

所有节点 value 都是同一个 `alpha`，排序没有意义。注释写“不要忘记预先评价”，但没有真正调用 `calcurmove()`。

`alpha_beta_PVS_select()` 也一样。应该在根节点先用 `fill_sort_inMoveNodes()` 或显式打分。

## 24. `quiescence_search()` 没有深度限制，存在深递归风险

约 L3053-L3128：

```cpp
int ChessAI::quiescence_search(int alpha, int beta) {
    ...
    for (auto& node : nextNodes) {
        MoveGuard guard(this, node);
        val = -quiescence_search(-beta, -alpha);
    }
}
```

静态搜索只靠“没有吃子/不被将军”停止。如果存在连续将军、连续吃子、重复追逐，递归可能很深。虽然 `searchTime.check()` 会超时抛异常，但它每 1024 次才检查一次，仍可能栈很深。

建议加静态搜索深度上限：

```cpp
int quiescence_search(int alpha, int beta, int qDepth) {
    if (qDepth <= 0) return evaluator.calstate(...);
}
```

## 25. `giveOutputBotzone()` 的异常兜底可能基于已损坏棋盘

约 L520-L539：

```cpp
try{
    ChessAI AI(&chess);
    AI.alpha_beta_PVS_select(AI.select);
    ...
}catch(const std::exception&){
    hasselectedmove = false;
}
```

由于 AI 直接操作外部 `chess`，而 `isQuietMove()`、空步裁剪异常等会破坏 `chess`，catch 之后 fallback 随机走子：

```cpp
chess.generateMovesWithForbidden(retMoves);
```

可能已经不是原始局面了。短期修复：AI 搜索时不要直接用外部棋盘，应复制一份：

```cpp
Chess searchBoard = chess;
ChessAI AI(&searchBoard);
```

选出 move 后再用原始 `chess` 验证。

# 建议优先修复顺序

第一优先级，必须先修：

1. 把 `getchessbook()` 函数体移动到 `Chess` 和 `Move` 定义之后。
2. 把类内 `int ChessAI::quiescence_search(...)` 改成 `int quiescence_search(...)`。
3. 修复 `isQuietMove()`：必须回撤，且返回语义要改成“安静走法”。
4. 禁用 `MoveNodeVoid()` 当前实现，改成真正 null move，并用 RAII 保证回撤。
5. 初始化并清空 `GridControl` 和 `havecontrol`。
6. 修复 `getGridcontrol()` 中兵横向控制的越界访问。
7. 修复 `getWin()` 的胜负符号。

第二优先级，影响棋力和规则正确性：

1. 统一红黑坐标系，尤其是 `resetBoard()`、`inKingArea()`、`calShapePenalty()`、评估表翻转。
2. 修复 `Chess::isattacked()` 的 King 判断。
3. 重写 `EvalRecord::isattacked()`，不要依赖 `board->currColor`。
4. `calstate()` 内部确保控制表对应当前局面。
5. 删除 PVS 中覆盖 LMR 结果的重复搜索语句。
6. 修复开局库最大 count 选择逻辑。
7. 给 `quiescence_search()` 加深度上限。

第三优先级，工程安全性：

1. `ChessAI` 禁止拷贝或改用 `unique_ptr`。
2. `EvalRecord::copyBoard()` 改名为 `bindBoard()`，明确非拥有关系。
3. `Move(string,string)` 增加长度和坐标校验。
4. `makeMoveAssumeLegal()` 增加 Debug/Release 都生效的前置检查。
5. 置换表增加 `valid` 位，并考虑重复局面历史对 TT 的影响。

整体判断：**当前版本最核心的错误不是某个估值参数，而是搜索过程中棋盘状态会被破坏。只要 `isQuietMove()` 和 `MoveNodeVoid()` 不修，PVS、LMR、置换表、静态搜索的结果都不可信。**
