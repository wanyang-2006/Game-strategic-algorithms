### 项目结构

　ElephantEye 的源程序包括9个模块，内容大致为：

(1) ucci.h/ucci.cpp

　　UCCI命令解释模块，包括 Windows 和 Unix 下的行输入接收程序；

(2) pregen.h/pregen.cpp

　　Zobrist 数组和着法预置表的生成模块。ElephantEye 的预置表分两个部分，一是滑动棋子的着法预置表(包括不吃子、车吃子、炮吃子和隔两子吃子)，它是实现位行和位列技术的基础；二是其他棋子的着法预置表，使得着法生成时避免了烦琐的边界判断。

(3) position.h/position.cpp

　　主要描述着法和局面的数据结构及功能。局面的处理是本模块的重点，处理内容包括局面初始化、FEN串导入、棋子移动、杀手着法的合理性判断、将军判断、长将和循环检测、子力价值分调整等过程，还包括5个子力位置价值表。

(4) genmoves.cpp

　　着法生成器，包括生成吃子着法和生成不吃子着法的两个，但不能只生成解除将军的着法。在生成吃子着法的同时赋予每个着法以相应的MVV(LVA)(或称准SEE)值。该模块还有一个专门判断棋子是否有保护的函数，来计算MVV(LVA)值，对于有保护的棋子，计算MVV-LVA的值(小于零不计)，对于无保护的棋子，只计算MVV的值。因此，判断棋子是否有根的程序也包括在本模块中。

(5) hash.h/hash.cpp

　　置换表、历史表和着法列表管理模块，包括置换表的分配和存取、主要变例获取等操作。

(6) book.h/book.cpp

　　开局库读取模块。

(7) movesort.h/movesort.cpp

　　着法列表排序模块。

(8) search.h/search.cpp

　　搜索模块，除了静态搜索、完全搜索和根结点搜索这三个主要过程外，还包括迭代加深控制、后台思考、时间分配、搜索参数统计和搜索信息输出等内容。该模块是整个程序的核心模块。

(9) eleeye.cpp

　　主程序(即 main 函数)。

(10) preeval.cpp

　　子力位置数组预生成器，ElephantEye 根据“进攻/防守”和“开局/中局/残局”两个参数线性调整子力位置数组。

(11) evaluate.cpp

　　局面评价函数，ElephantEye 采用了四级偷懒评价的机制，最粗的层次只评价特殊棋型，进一层次评价牵制，再进一层次评价车的灵活性，最高层次还评价马的阻碍。

### 核心算法与总体设计思路分析

ElephantEye (象眼) 是一个高度优化的中国象棋UCCI引擎，其核心设计思路围绕着“高效的搜索博弈树”和“精准的启发式评估”展开。以下是该程序中使用的主要算法和设计模式总结：

#### 1. 棋盘表示与着法生成 (position/pregen)

* **数组/位列表示法**：采用了高效的底层数据结构。通过预置表(Pregen)和滑动掩码(SlideMask)大幅减小边界判断和吃子合法性判断的开销。
* **Zobrist 哈希技术**：在局面变化时，通过异或(XOR)随机生成的64位/32位键值，快速计算当前局面的唯一哈希值，为置换表(Transposition Table)提供极速的索引。

#### 2. 搜索算法 (search)

* **Alpha-Beta 剪枝核心**：结合极小极大(Minimax)算法的变体，剔除明显较劣的分支，指数级减少搜索节点。
* **迭代加深搜索 (Iterative Deepening)**：从浅层开始搜索，利用浅层搜索保存下来的置换表和最佳着法路线(PV)，极大地优化深层搜索时的着法顺序，使得剪枝效率最大化。
* **静态搜索 (Quiescence Search)**：在 Alpha-Beta 搜索达到叶子节点时，如果不加限制地直接评估，可能会遇到“水平线效应”(Horizon Effect)。静态搜索会继续对吃子等剧烈变化的着法进行展开，直到局面平稳后再调用评价函数。
* **空步裁剪 (Null Move Pruning)**：在己方具有优势且局面不是非常危险的状况下，假装放弃一步棋，如果即使这样对方也无法获胜，就能安全地剪除这棵博弈树的大量子树。

#### 3. 着法排序启发发法 (movesort/genmoves)

在进行 Alpha-Beta 搜索时，着法的评估顺序直接决定了剪枝的效率。系统按照以下顺序排序着法(Phase分阶)：

* **置换表着法 (Hash Move)**：之前搜索过的该局面的最优着法，优先级最高。
* **好的一步吃子 (Good Captures / MVV-LVA)**：使用“最有价值的牺牲者/最没价值的攻击者”启发(MVV/LVA)。用兵吃对方的车，优先级极大；用车吃对方的兵，优先级较小。并在生成着法时考虑了是否有保护(SEE近似)。
* **杀手启发 (Killer Heuristic)**：保存同层搜索中引起剪枝的非吃子着法(杀手着法)，在其他兄弟节点中优先考虑。
* **历史启发 (History Heuristic)**：对于不吃子的平淡着法，程序记录它们在历史搜索中引发剪枝的次数，次数越多的着法排序越靠前。底层使用了快速的 Shell Sort (希尔排序) 来对着法列表进行重排。

#### 4. 置换表 (hash)

* **双层替换策略 (Two-Tier Replacement)**：置换表利用探测(Probe)和记录(Record)减少重复节点的搜索。程序使用了一定深度的层级保存规则，部分位置“始终替换”(存储最新)，部分位置“深度优先”(保留深层搜索出的结果以防止高价值数据被覆盖)。

#### 5. 局面评价 (evaluate)

* **延时/偷懒评价 (Lazy Evaluation)**：象棋评估涉及大量复杂的棋型检查。系统按层次计算子力价值和位置评分，通过逐级判断决定是否还要进行更高代价的检查(如牵制、灵活性、马脚阻碍等)。当基础分(材质优势等)已经远超Alpha-Beta边界时，程序会偷懒提前返回结果，节省了大量的CPU时钟周期。

在这个引擎（ElephantEye）的“不吃子着法生成”（`GenNonCapMoves`）函数中，**着法本身在生成阶段并没有直接进行评分**。

我们可以看到代码中记录不吃子着法的方式仅仅是：

```cpp
lpmvsCurr->dwmv = MOVE(sqSrc, sqDst);
lpmvsCurr ++;
```

注意它用的是联合体字段 `dwmv`，一次性赋值了32位（包含16位着法 `wmv`，并把前16位的分数 `wvl` 默认置为0或没有显式计算分数），而没有像吃子着法那样调用 `MvvLva` 去显式设置 `wvl` 字段。

那么，不吃子着法是如何评分和排序的呢？
它是由 **历史启发（History Heuristic）算法** 提供的分数，这写在 `movesort.cpp`（着法排序模块）中。

具体流程如下：

1. **着法生成阶段**：`GenNonCapMoves` 只是把所有合法的空步（不吃子）塞进列表，不负责打分。
2. **拉取历史得分**：在 `movesort.cpp` 的 `MoveSortStruct::SetHistory(void)` 函数中，会统一给这些不吃子的着法赋分：
   ```cpp
   // 取出该着法在全局历史表 (nHistory) 中的得分
   vl = nHistory[mvs[i].wmv];
   // 然后通过一定位移算法转换为用于排序的分数，存回 mvs[i].wvl 中
   ```
3. **历史分怎么来的**：在搜索（Search）过程中，如果某个“不吃子着法”引起了 Beta 剪枝（证明是一步好棋），引擎会调用 `SetBestMove(int mv, int nDepth, uint16_t *lpwmvKiller)`，这个函数会把当前的搜索深度相关的分数累加进一个全局巨大数组 `nHistory[mv]` 中（这是通常的 Butterfly 算法，深度平方累加）。
4. **排序阶段**：紧接着 `SetHistory()`，引擎会调用 `ShellSort()` 来把分数高的（历史表现好的）不吃子着法排在前面优先搜索。

**总结**：
不吃子着法在**生成时（genmoves.cpp）没有硬编码的启发分（评分为0或未设定）**，它的分数来源是在**排序模块（movesort.cpp）中动态根据历史剪枝成功率映射过来的“历史表得分”**。

问题与疑惑：：

问：

程序原有的思路中，能保证置换表着法一定比杀手着法要好吗？为什么置换表着法要在两个杀手着法之前？

答：

**不能保证置换表着法一定比杀手着法好（在最终搜索完成的意义上），但它的“命中率”和“针对性”是最高的。**

在Alpha-Beta剪枝的着法排序（Move Ordering）中，把置换表着法排在最前面、杀手着法随后，有以下几个核心原因：

### 1. 针对性不同：精确匹配 vs 相似猜测

* **置换表着法（Hash Move）：属于“精确记忆”。** 它是引擎在之前的搜索历史中（比如迭代加深时较浅深度的搜索，或者通过不同的下棋顺序碰巧走到过这个局面时），针对**当前的精确盘面**算出来的最佳着法或截断着法。
* **杀手着法（Killer Move）：属于“经验借用”。** 它是引擎在搜索**同一深度下的其他分支（兄弟节点）**时，发现的能导致剪枝的厉害着法。引擎假设“在相似的局面下，同一步好棋可能依然奏效”。

**结论：** 置换表提供的建议是针对当前局面的“私人定制”，而杀手着法只是同一层级的“通用经验”。因此，置换表着法的可信度远高于杀手着法。

### 2. 信息质量不同：实际计算 vs 瞎蒙

* 置换表着法是经过引擎切实评估和搜索树展开后得出的结论。
* 杀手着法在当前局面下甚至可能是一步**不合法的废棋**（代码中你在看杀手着法时，总要先通过 `pos.LegalMove()` 验证一下它能不能走）。把一个连是否合法都不确定的猜测排在精确计算过的经验之前显然是不合理的。

### 3. 追求最高概率的剪枝（Beta/Cutoff）

在Alpha-Beta算法中，着法排序的终极目的只有一个：**尽快找到一个能引发截断（Cutoff）的着法，从而直接忽略剩下的所有着法。**
引擎并不需要一开始就找出绝对最好的棋，只要先测试的那步棋“足够好”就行了。统计表明：

1. **置换表着法**引发截断的概率极高，通常在 **80% - 90%** 左右。
2. 如果置换表失效，**杀手着法**往往能提供额外的 **5% - 10%** 的有效补充。
3. 剩下的再靠吃子启发（MVV/LVA）和历史表（History Table）兜底。

因此，**按照“剪枝概率从高到低”试错**，把置换表排在第一、杀手着法排第二，是长期博弈程序发展下来证实的最优化数学期望计算时间最短、效率最高的黄金法则。

怎样去构建类——面向对象设计的观点来设计

在编写国际象棋、中国象棋等棋类博弈程序时，这是一个非常核心且经典的设计问题。

直接给出结论：**从程序性能和业界惯例来看，博弈树的节点在实际的数据结构中往往只保存“着法 (Move)”以及评价分数等极少量信息，绝对不应该在每个树节点中保存完整的“棋局状态 (`vector<vector<Grid>>`) ”。**

尽管在理论和数学概念上，博弈树的节点（Node）代表的是“局面状态”，边（Edge）代表的是“着法”，但在实际编写代码时，这两者的处理方式有巨大的差异。以下是具体的原因和实现惯例解答：

### 1. 内存与性能瓶颈（为什么不能存状态？）

中国象棋的平均分支因子（每一步合法的走法数量）在40左右。如果你要向前搜索至少 4 层到 6 层，博弈树在最坏情况下会展开 $40^4$ (256万) 到 $40^6$ (40亿) 个节点。

* **内存爆炸**：如果你在每个节点里保存一次 `vector<vector<Grid>> state`（即使只有一层的 state），这会占用海量的堆内存，程序会瞬间 Out Of Memory 崩溃。
* **频繁分配与拷贝极慢**：面向对象语言中 `vector` 的深层拷贝是非常消耗 CPU 时间的，会导致你的算法绝大部分时间都在拷贝棋盘，而不是在计算走法。

### 2. 业界惯例：状态复用与“隐式博弈树”（如何实现？）

经典的象棋AI引擎（如你文件夹中的“象眼 EleEye”、Stockfish等）采用的都是**“单一状态、递归搜索”**的模式：

整个程序（或者每个搜索线程）内部**只维护一个全局的棋局状态对象**（即你现有的 `Chess` 类）。博弈树并不作为一棵庞大的树形数据结构（如包含多层的 `TreeNode` 链表）在内存中真实存在，而是表现为代码的**递归调用栈**。

具体的搜索惯例（如 Alpha-Beta 剪枝）范式如下：

1. 产生当前状态下所有合法的**着法 (Move)**。
2. 遍历这些着法，对当前共享的棋盘执行走子（`Make Move`）。
3. 进行递归调用（进入博弈树下一层）。
4. （非常重要）**撤销走子（`Undo Move`），恢复棋盘原状**，以便尝试下一个着法。

### 3. 结合你目前代码的实现优势

你当前的代码基础其实已经具备了按业界惯例来实现博弈树的核心要素：
你在 `Chinese_Chess_trial_1.cpp` 中已经写好了：

* `makeMoveAssumeLegal(const Move &move)`：执行着法并推进状态。
* `undoMove()`：撤销着法回退状态。

这意味着你**完全不需要设计一个包含 state 的 Node 结构体**。你只需要在一个搜索函数里这样写（概念展示）：

```cpp
int ChessAI::alphaBetaSearch(int depth, int alpha, int beta, bool isMaxPlayer) {
    if (depth == 0 /* 或分出胜负 */) {
        // 直接根据当前的 board->state 计算估值
        return evaluateCurrentBoard(); 
    }

    // 只需要获取 Move 集合
    vector<Move> legalMoves;
    board->generateMovesWithForbidden(legalMoves, true);

    if (isMaxPlayer) {
        int maxEval = -INFINITY;
        for (const auto& move : legalMoves) {
            // 1. 在当前共享棋盘上施加改变
            board->makeMoveAssumeLegal(move); 
            // 2. 递归进入下一层
            int eval = alphaBetaSearch(depth - 1, alpha, beta, false);
            // 3. 还原棋盘状态
            board->undoMove(); 
  
            maxEval = std::max(maxEval, eval);
            alpha = std::max(alpha, eval);
            if (beta <= alpha) break; // 剪枝
        }
        return maxEval;
    } else {
        // ... MinPlayer 逻辑类似 ...
    }
}
```

#### 着法作为隐式节点的桥梁

当你从 A 局面衍生到 B 局面时，程序做的仅仅是执行这一步着法（Make Move），往下递归搜索，返回分值后，再立刻撤销这一步着法（Undo Move/UnMake Move），让棋盘恢复原状，随后再尝试下一种走法。
在这期间，并不用重新实例化任何“局面类”。也就是如你所见 search.cpp 中的 Search.pos.MakeMove(mv) 和 Search.pos.UndoMakeMove() 的操作组合。这被叫做“微差更新”（Incremental Update）。它极大地节省了开销。
