**结论：当前程序在正常中开局局面下不能实际搜索到 10 层。**
更准确地说：代码名义上设置了 `max_depth = 10`，但在默认 `800 ms` 时间限制下，初始局面实测只能 **完整完成 3 层** ，然后在搜索第 4 层时超时。代码确实是迭代加深 `d = 1 ... 10`，超时时会保留上一层完整结果；因此“正在搜第 4 层超时”不等于完成了 4 层，而是只完成了 3 层。

## 1. 定量实测结果

我用当前搜索逻辑对初始局面做了一次基准测试，结果如下：

| 限制搜索深度 | 完整完成所需时间 | `searchTime.check()`调用数 |
| -----------: | ---------------: | ---------------------------: |
|         1 层 |          11.8 ms |                          456 |
|         2 层 |          86.8 ms |                        6,390 |
|         3 层 |         523.9 ms |                       42,718 |
|         4 层 |       2,676.7 ms |                      366,760 |
|         5 层 |        19,309 ms |                    2,123,303 |

默认 800 ms 下，程序输出等价于：

[
\text{timeout at } d=4
]

所以：

[
D_{\text{completed}}=3
]

因为完整 4 层需要：

[
2676.7\text{ ms} > 800\text{ ms}
]

因此当前默认配置下， **连 4 层都不能稳定完整完成，更不可能完成 10 层** 。

## 2. 为什么 10 层不现实

当前搜索入口中：

```cpp
int max_depth = 10;
for (int d = 1; d <= max_depth; d++)
```

这说明 10 层只是“目标深度”。同时 `SearchTime` 默认时间限制是 800 ms，并且超时后会抛出 `TimeOutException`。

关键瓶颈有四个。

### 第一，初始实际根分支已经是 44

初始局面根节点合法着法数实测为：

[
B_0=44
]

即使后续平均有效分支因子经过 PVS、αβ、置换表、空步裁剪后下降，10 层仍然非常大。

如果完全不剪枝，10 层单次搜索节点量约为：

[
\sum_{i=1}^{10}44^i
\approx 2.78\times 10^{16}
]

迭代加深还会重复搜索浅层，总节点量约为：

[
\sum_{d=1}^{10}\sum_{i=1}^{d}44^i
\approx 2.85\times 10^{16}
]

这当然完全不可运行。

### 第二，即使用理想 Alpha-Beta，10 层仍远超 800 ms

理想 αβ 剪枝复杂度近似：

[
O(B^{D/2})
]

用初始分支 (B=44)，10 层理想节点数约：

# [

2B^{D/2}-1

# 2\times44^5-1

329,832,447
]

而 800 ms 实测时，`check()` 调用速率约为：

[
\frac{72,960}{0.8017}
\approx 91,000\ \text{次/秒}
]

即使粗略把一次 `check()` 当作一个搜索节点量级，理想 αβ 的 10 层也需要：

[
\frac{329,832,447}{91,000}
\approx 3624\text{ 秒}
\approx 60.4\text{ 分钟}
]

这已经是 **理想剪枝下限估计** ，仍然比 800 ms 大约：

[
\frac{3624}{0.8}\approx4530
]

倍。

### 第三，实测增长率外推，10 层约为几十小时量级

从完整搜索深度 3、4、5 的实测时间看：

[
T_3=0.524s,\quad T_4=2.677s,\quad T_5=19.309s
]

用深度 3 到 5 的对数线性拟合，平均每加一层约乘：

[
r\approx6.07
]

所以从 5 层外推到 10 层：

# [

T_{10}
\approx
T_5\times r^5

19.309\times6.07^5
\approx150,345s
]

即：

[
T_{10}\approx41.8\text{ 小时}
]

即使用较乐观的增长倍数 (r=5.79)：

[
T_{10}\approx34.9\text{ 小时}
]

用较悲观的 (r=7.2)：

[
T_{10}\approx103.8\text{ 小时}
]

因此当前 800 ms 预算下，10 层不是“稍微差一点”，而是相差大约：

[
\frac{150,345}{0.8}
\approx187,900
]

倍。

## 3. 代码层面的主要原因

**1. 到叶子还会进入静态搜索。**
`alpha_beta_PVS_search(depth == 0)` 不直接评估，而是调用 `quiescence_search(alpha, beta)`；静态搜索默认最大深度为 15。也就是说主搜索 10 层之外，还可能继续搜吃子/应将变化。

**2. 合法着法生成很重。**
`generateMovesWithForbidden()` 先生成全部着法，再对每步调用 `repeatAfterMove()` 过滤重复局面；`repeatAfterMove()` 会临时落子、沿历史状态比较、再撤销。

**3. 每次落子复制整张棋盘。**
`makeMoveAssumeLegal()` 里有：

[
vector copyState = state[currTurnId]
]

也就是每下一步复制 90 格棋盘。搜索节点很多时，这个成本非常明显。

**4. 根节点没有共用 alpha。**
在 `alpha_beta_PVS_select()` 中，每个根着法都重新设置：

[
\alpha=-999999,\quad \beta=999999
]

注释里也写了“所有根节点着法不再公用一个 alpha”。这会削弱根层 αβ 剪枝效果：前一个根着法搜出的好结果，不能帮助后面的根着法快速截断。

---

## 4. 最终判断

当前程序：

[
\boxed{\text{名义最大深度}=10}
]

但默认 800 ms 下：

[
\boxed{\text{实际完整深度}\approx3}
]

初始局面完整 4 层已需要：

[
2.68s
]

完整 5 层需要：

[
19.3s
]

完整 10 层按实测增长率外推约：

[
35\sim104\text{ 小时}
]

较中心的拟合估计为：

[
\boxed{T_{10}\approx41.8\text{ 小时}}
]

所以答案是：

[
\boxed{\text{当前程序实际不能搜索到 10 层；800 ms 下通常只能完整到 3 层左右。}}
]
