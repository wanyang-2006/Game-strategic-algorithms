# Gemini 3.1 Pro preview


### 1. 为什么双方一上来就吃子？

这与你的《中国象棋》规则系统实现以及初始棋盘布局机制有关。不仅不是 Bug，反而在你现有的合法着法生成器（`generateMoves`）中是一个**完全合法的走法**！

在你的 C++ 代码中，判定炮（Cannon）是否能吃子的规则主要是通过 `betweenNotEmptyNum == 1`（起点与终点之间恰好只有一颗棋子）来处理的。

* 在标准的中国象棋开局布局中，你设定的底层坐标是：红方左炮在 B3 对应的 `(1, 2)`，而黑方的左马在 B10 `(1, 9)`，黑方左炮在 B8 `(1, 7)`。
* 此时对于红棋 `炮(1,2)` 向前方直线检索，沿途坐标中 `(1,3), (1,4), (1,5), (1,6), (1,8)` **全都是空的**（因为兵位于偶数列：0, 2, 4, 6, 8，所以在第 1 列上没有兵）。
* 这意味着，在 `(1,2)` 红炮和 `(1,9)` 黑马之间，**仅隔着一枚棋子**：也就是 `(1,7)` 处的黑炮。
* 既然 `betweenNotEmptyNum == 1` 成立，你的 `Cannon` 吃子逻辑就会认为红炮跃过黑炮去吃掉黑马是“完美合法”的棋步！

并且由于你此时挂载的无开局库（无先验知识），AI 会进行纯粹的静态/动态评估，MVV/LVA 处理时认为第一回合吃掉黑马可以获得大量“吃子评分”，从而毫不犹豫地下出了 **“炮二进七”（直接吃挂对面的马）** 这样虽然合乎你设定规则、但明显违背正常下棋基本逻辑的“自杀式换子”。而在第二回合，黑方出于完全相同的理由，也选了 **“炮8进7”（黑炮打你的红马）**。

### 2. 为什么只有三个回合，就出现了输入不合法（INVALID_INPUT_VERDICT）的情况？

Botzone 平台的 `INVALID_INPUT_VERDICT` 通常不会指你的局面内部评分错误，而是指 **程序超时被平台强制杀掉（没有向标准输出任何内容打印出 JSON）** 或 **程序遭遇了未捕获的 C++ 崩溃报错**。结合图片可见该回合 Red Player 的输出（玩家输出）为字面上的 **“无”**，以下两个原因是导致这一现象的罪魁祸首：

**原因一：PVS搜索+静态搜索 遭遇性能爆炸（致命超时导致进程被平台强杀）**

* **情况突变**：第1会合和第2回合大家都处于极具约束力的初始盘面，搜索分支相对较少，AI 能够快速遍历完成。但是等到第 3 回合初，双方的马都被吃了，边路炮线豁然开朗，导致能够产生的**高优先吃子步和空步急剧增多**。
* **搜索树太深**：你设定了基础极大极小搜索深度 `max_depth = 10`，同时底层挂勾了基于取舍阶段的 `quiescence_search`（静态搜索，最大深度又达到 15）。中象的分支因子本身极大（约莫 40 左右），加之你对静搜的触发（比如所有的将/吃子都要深挖）缺乏极其严格的裁剪，导致在第3回合局面一变，搜索节点数随之爆炸。
* **自定义计时器未阻止强杀**：虽然你写了 `SearchTime::check()`，但是它里面运用了 `(& 255) == 0` 来降低频次。面对爆发式增加的递归节点，如果 Botzone 规定 1 秒或 2 秒就要给出输出，你的 AI 是直接超出了物理限界被系统平台外部 Killed 掉，连执行 `Json::FastWriter writer; cout << writer.write(ret) << endl;` 的机会都没有，所以输出显示为“无”。

**原因二：`getInputBotzone` 异常未捕获导致程序非正常终止（闪退Crash）**
在代码中重现对局进展时：

```cpp
if (!chess.isMoveValidWithForbidden(curMove)){
    throw std::runtime_error("input is not valid!");
}
```

如果在第3回合（这是红方第二次行动，因此这段对局还原历史的代码第一次需要同时模拟 `responses[0]` 和 `requests[1]`），若中途因为长将规则 `repeatTime >= 3` 与 Zobrist 或棋盘越界触发等任意微小偏差，导致 `isMoveValidWithForbidden("h7h0")` 失败，就会抛出 `std::runtime_error("input is not valid!")`。而你在 `main()` 中未采用 `try-catch` 捕获该异常，导致在真正交给 AI 前程序就发生了 Crash，无法打印合法 JSON 输出。

**修复建议**：

1. 取消开局库的情况下，必须严加控制 `ChessAI::alpha_beta_PVS_select` 初始的 `max_depth`（降至 4~6），防止一旦战局散开节点呈指数暴增。
2. 在 `main()` 的 `getInputBotzone` 外部追加 `try-catch`，使得即使解析历史招法失败，也能强行输出预设的随机走步或直接输出 `{"source":"-1", "target":"-1"}` 认输，以满足平台评测机制，以便进一步查看报错而不是出现 `INVALID_INPUT_VERDICT`。
