## 核心结论

这不是单纯“搜索不够深”的问题，而是 **评估函数、攻击/威胁判定、迭代加深超时处理、以及部分剪枝逻辑共同把搜索方向带偏** 。所以把 `search_time` 从 600ms 提到 800ms，或把 PVS 深度上限从 10 提到 30，基本不会产生质变；程序只是更努力地搜索一个错误的评价体系。

从日志看，开局直接出现 `e0 -> e1`、`e9 -> e8`、`e1 -> e2` 这类动帅/将走法，后面也反复出现将帅、士的无意义移动；我按日志重放统计，228 个半回合中，将/帅走了 45 次，士走了 28 次，二者合计约三分之一，而真正吃子只有 24 次。这与视频里“有吃子不吃、送子、无威胁动将帅士”的现象一致。

---

## 1. 为什么程序对吃子尤其不敏感？

### 第一层原因：吃子分只用于“排序”，不是最终决策

代码里 `calcurmove()` 对吃子用了 MVV-LVA 类似的分数，非吃子返回 0，吃子返回 `CaptureBaseScore + VictimValue * 10 - AttackerValue`。这看起来像“吃子优先”，但它只在 `fill_sort_inMoveNodes()` 里用于 **着法排序** ，随后 PVS 会重新搜索并用 `calstate()` 的结果覆盖 `MoveNode.value`。也就是说，吃子最多只是“先被搜索”，并不保证最终被认为好。

问题在于最终评价 `calstate()` 本身没有稳定地表达“多一个车/马/炮/兵”的价值。它主要依赖棋子位置表，车大约 180～230，炮约 90～106，马约 85～108，兵/帅共用一套表，甚至高级兵或帅的位置分可以接近炮马。这样会导致程序认为“动帅到高分位置”“调一个子到位置表高分点”可能和吃子差不多，甚至更好。

### 第二层原因：动态攻击控制表几乎没有真正参与评价

`caldynamicstate()` 使用 `GridControl`，`hasattackchance()` 使用 `havecontrol`，但当前 `calstate()` 里没有在评价前调用 `getGridcontrol()`。因此 `GridControl` 和 `havecontrol` 很可能长期保持初始值或过期值，导致“我有没有攻击机会”“控制了哪些点”“是否存在吃子机会”没有被可靠地计入分数。代码里 `getGridcontrol()` 是单独定义的，但 `calstate()` 只是调用 `calstaticstate()` 和 `caldynamicstate()`。

这会直接造成你看到的现象：程序即使眼前有吃子机会，最终 `calstate()` 也未必把这个机会当成明显优势。

### 第三层原因：被攻击、送子、保护关系的符号和判定都有问题

`calstaticstate()` 中士/象被威胁时使用的是 `mid_AdvBis_Threat`，而这张表的数值普遍比 `mid_AdvBis_no_Threat` 更高。代码对己方士/象是：

```cpp
res += flag ? mid_AdvBis_Threat[posIndex] : mid_AdvBis_no_Threat[posIndex];
```

这等于在某些位置上 **己方士/象被威胁反而加分** 。这会削弱“不要送子”的意识。

另外，`Chess::isattacked()` 中对士的攻击范围判断也有明显方向错误：士属于本方九宫，但代码判断时使用了 `oppColor(color)` 的九宫。象的攻击判断也缺少是否过河的限制。这会让“某格是否被攻击”“某吃子是否被保护”出现误判，从而影响 MVV-LVA、静态搜索、威胁判断、LMR 安静着法判断等多个模块。

### 第四层原因：没有真正的“送子惩罚”或 SEE

目前程序没有静态交换评价 SEE。它只粗略判断“目标子是否被保护”，然后用很小的 `VictimValue / AttackerValue` 判断是否剪掉某些吃子。这个价值表是：

```cpp
King=5, Rook=4, Knight=3, Cannon=3, Pawn=2, Bishop=1, Assistant=1
```

这个表只适合非常粗糙的排序，不适合判断交换是否亏损。结果就是：程序既可能错过好吃子，也可能认为送车、送炮只是位置表损失，而不是严重物质损失。

## 2. 为什么会出现大量毫无意义的着法，例如无威胁时动将/帅/士？

最直接的原因是： **将/帅和兵共用同一套位置表** 。

在 `calstaticstate()` 里：

```cpp
case Pawn:
case King: {
    bool flag = this->hasattackchance(x, y);
    midValue = flag ? mid_KingPawn_attack[posIndex] : mid_KingPawn_no_attack[posIndex];
    ...
}
```

这会把“兵往前冲的价值”错误地套到将/帅身上。以当前表为例，红帅从 `e0` 到 `e1`，位置表分值会明显上升；黑将从 `e9` 到 `e8` 也同理。因此程序开局第一步就走 `e0 -> e1`，黑方也走 `e9 -> e8`，这不是搜索偶然，而是评价函数在鼓励这种行为。

第二个原因是开局库被注释掉了。`giveOutputBotzone()` 里“优先使用开局库”的逻辑被整段注释，程序从第一步就完全依赖搜索和评价函数。对于一个还没有稳定物质评估、王安全评估、开局发展评估的引擎来说，开局很容易走出动帅、动士这种“位置表看起来涨分”的怪招。

第三个原因是程序没有给“无意义王/士移动”足够惩罚。它只生成合法着法，然后让搜索自己选；但评价函数里没有“开局不要动帅”“无将军不要离开原位”“士象不要无意义来回移动”“重复移动扣分”“发展子力加分”等稳定项。因此只要位置表或局部搜索觉得这步略好，就会选出来。

---

## 3. 为什么增加运行时间和搜索深度仍然没有显著提升？

### 3.1 深度上限 30 不等于实际搜到 30 层

当前 PVS 入口已经写成 `max_depth = 30`，并且使用迭代加深，从 1 层搜到 30 层。但 800ms 的时间限制下，中国象棋分支因子很高，再叠加 `generateMovesWithForbidden()`、重复局面检测、静态搜索、置换表、LMR、空步裁剪等开销，实际不可能稳定完成 30 层。日志里前 100 多个半回合大多耗时约 900ms，说明程序经常是在时间边界附近被打断，而不是完整搜完高深度。

所以把上限从 10 改成 30，通常只是让它“允许搜更深”，并不代表它真的搜到了更深。

### 3.2 超时后保留的是“可能未完成的一层”

当前迭代加深逻辑在超时时直接 catch，然后保留当前 `selected`。如果超时发生在某一层的中途，前几个着法可能已经被更新为较深层分数，后面的着法仍然是上一层甚至初始排序分数。最后直接 sort，就会把不同深度、不同可信度的分数混在一起排序。

这会导致一个很典型的现象：加大深度或时间后，结果不一定更稳定，甚至可能更随机。正确做法是：每完成一整层后保存 `lastCompleted`；如果下一层超时，回退到上一层完整结果，而不是使用半层结果。

### 3.3 搜索越深，只会更坚定地相信错误评价

如果评价函数认为 `e0 -> e1` 是好棋，认为士象被威胁不一定坏，认为兵/帅位置分可以和吃子收益相抗衡，那么搜索越深只是更努力地证明这些错误偏好。深搜不能替代正确的物质价值、王安全、送子惩罚和攻击判定。

### 3.4 空步裁剪、LMR、安静着法判断依赖错误的威胁检测

PVS 中使用了空步裁剪、LMR、killer move、TT move ordering 等优化。这些优化本身没问题，但前提是“局面是否有威胁”“这步是否安静”“这个子是否被攻击”的判断要可靠。当前这些判断依赖 `havethreat()`、`isattackedBy()`、`Chess::isattacked()`，而攻击判定存在前面提到的方向/过河/符号问题。因此剪枝可能剪掉关键战术线，或者把垃圾安静着法当作高价值着法。

## 建议修改顺序

### 第一步：先修评价函数，不要先继续加深搜索

把“物质价值”和“位置价值”分开。建议先加入明确的物质分：

```cpp
static constexpr int PieceValue[8] = {
    0,        // None
    100000,  // King
    120,      // Bishop / Elephant
    270,      // Knight
    500,      // Rook
    60,       // Pawn，过河后可另加
    285,      // Cannon
    120       // Assistant
};
```

然后在 `calstaticstate()` 中至少做到：

```cpp
int material = PieceValue[curGrid.type];
int pst = getPieceSquareValue(curGrid.type, curGrid.color, x, y);

if (curGrid.color == color) {
    res += material + pst;
} else {
    res -= material + pst;
}
```

位置表只作为几十以内的小修正，不要让位置分压过车、马、炮的物质价值。

### 第二步：将/帅不能再用兵表

把：

```cpp
case Pawn:
case King:
```

拆开：

```cpp
case Pawn:
    // 使用兵卒位置表
    break;

case King:
    // 使用王安全表，或者只给很小的位置分
    // 开局/中局离开安全位置应扣分
    break;
```

王的评价建议非常保守：不被将军、不暴露、不与对方重子形成空头炮/空头车威胁，比“往前走”重要得多。开局无威胁时，帅/将离开原位应当扣分，而不是加分。

### 第三步：修复 GridControl 的更新

如果继续使用 `GridControl` 和 `havecontrol`，`calstate()` 开头必须更新控制表：

```cpp
int EvalRecord::calstate(vector<Grid>& target, colorType color) {
    getGridcontrol(); // 当前版本至少要加这个
    int res = 0;
    res += calstaticstate(target, color);
    res += caldynamicstate(target, color);
    ...
    return res;
}
```

更好的做法是把 `getGridcontrol()` 改成：

```cpp
void EvalRecord::getGridcontrol(const vector<Grid>& target);
```

不要直接读 `board->state[currTurnId]`，否则以后对临时局面、拷贝局面、静态测试局面评分时会出错。

### 第四步：修复攻击判定

`Chess::isattacked()` 中士和象的判断建议改成合法走法语义：

```cpp
case Assistant:
{
    if (inKingArea(mx, my, color) &&
        abs(dex) == 1 && abs(dey) == 1) {
        return true;
    }
    break;
}

case Bishop:
{
    if (inColorArea(mx, my, color) &&
        abs(dex) == 2 && abs(dey) == 2) {
        int ex = x + dex / 2;
        int ey = y + dey / 2;
        if (state[currTurnId][xy2pos(ex, ey)].color == EMPTY) {
            return true;
        }
    }
    break;
}
```

这里的 `color` 是攻击方颜色，目标点必须在攻击方士/象的合法活动区域内。

### 第五步：修正士象“被威胁加分”的问题

己方子被攻击应扣分，敌方子被攻击才加分。不要使用“Threat 表更高所以加分”的写法。可以先简单改为：

```cpp
bool attackedByEnemy = isattackedBy(oppCol, x, y);

if (curGrid.color == color) {
    res += base;
    if (attackedByEnemy) {
        res -= PieceValue[curGrid.type] / 8;
    }
} else {
    res -= base;
    if (isattackedBy(color, x, y)) {
        res += PieceValue[curGrid.type] / 10;
    }
}
```

后续再用 SEE 替代这个粗略威胁项。

### 第六步：修复迭代加深超时处理

不要在超时后直接使用半层搜索结果。建议改为这种结构：

```cpp
void ChessAI::alpha_beta_PVS_select(vector<MoveNode>& selected) {
    int maxDepth = 30;
    vector<Move> tmpMoves;
    board->generateMovesWithForbidden(tmpMoves);

    selected.clear();
    fill_sort_inMoveNodes(selected, tmpMoves);

    vector<MoveNode> lastCompleted = selected;

    searchTime.start();

    try {
        for (int d = 1; d <= maxDepth; ++d) {
            vector<MoveNode> work = lastCompleted;

            int alpha = minstateval;
            int beta = maxstateval;

            for (auto& node : work) {
                searchTime.check();

                int score;
                {
                    MoveGuard guard(this, node);
                    score = -alpha_beta_PVS_search(d - 1, -beta, -alpha);
                }

                node.value = score;
                if (score > alpha) {
                    alpha = score;
                }
            }

            sort(work.begin(), work.end(), MoveNodecmp);
            lastCompleted = work;
            selected = lastCompleted;
        }
    } catch (const TimeOutException&) {
        selected = lastCompleted;
    }

    sort(selected.begin(), selected.end(), MoveNodecmp);
}
```

同时把当前函数里的：

```cpp
for(auto& Node : select)
```

改成：

```cpp
for(auto& Node : selected)
```

当前调用刚好传的是 `AI.select`，所以这个 bug 不一定每次触发；但这是危险写法，后续一旦传入局部 vector，搜索会失效。

### 第七步：修复空步裁剪

PVS 里的空步裁剪应该只下一次空步，并且不要在被将军、残局、疑似 zugzwang 局面使用。建议写成：

```cpp
if (depth >= 3 && !inCheck(board->currColor) && hasNonPawnMaterial(board->currColor)) {
    int nullVal;
    {
        NullMoveGuard guard(this);
        nullVal = -alpha_beta_PVS_search(depth - 1 - R, -beta, -beta + 1);
    }

    if (nullVal >= beta) {
        return beta;
    }
}
```

你当前另一个 `alpha_beta_search()` 版本里有“先 `MoveNodeVoid()`，再 `NullMoveGuard`，然后又手动 `undoNullMove()`”的双重空步/双重回撤风险；即使当前主要走 PVS，也建议统一修掉。

### 第八步：加入真正的 SEE 或至少简单送子惩罚

先用简单版也可以：

```cpp
int hangingPenalty(colorType side) {
    int penalty = 0;
    colorType enemy = board->oppColor(side);

    for (int y = 0; y < 10; ++y) {
        for (int x = 0; x < 9; ++x) {
            const Grid& g = board->state[board->currTurnId][board->xy2pos(x, y)];
            if (g.color != side || g.type == King || g.type == None) continue;

            bool attacked = evaluator.isattackedBy(enemy, x, y);
            bool defended = evaluator.isattackedBy(side, x, y);

            if (attacked && !defended) {
                penalty += PieceValue[g.type] / 3;
            } else if (attacked) {
                penalty += PieceValue[g.type] / 10;
            }
        }
    }

    return penalty;
}
```

然后在 `calstate()` 中：

```cpp
res -= hangingPenalty(color);
res += hangingPenalty(oppCol);
```

这一步会明显减少“把车马炮送到对方嘴边”的情况。

## 最小可行修复方案

优先级最高的是这五项：

1. **King 和 Pawn 分表** ：将/帅绝不能再使用兵卒前进表。
2. **加入真实物质价值** ：车、马、炮、兵、士象必须有稳定物质分。
3. **修复 `getGridcontrol()` 调用** ：否则攻击机会和动态控制基本失效。
4. **修复 `isattacked()` 中士/象攻击范围** ：否则保护、威胁、送子判断都不可靠。
5. **迭代加深只保留完整层结果** ：不要用超时半层结果排序。

完成这五项后，再调 `search_time` 和 PVS 深度才有意义。否则当前程序的主要问题不是“看得不够远”，而是“看见了也评价错了”。
