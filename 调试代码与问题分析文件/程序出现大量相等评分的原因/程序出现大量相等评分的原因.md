结论：**日志中大量“走法不同但得分相同”，主要不是棋盘状态被污染造成的，而是搜索函数把 Alpha-Beta / PVS 的“边界值”当成了每个根节点着法的真实精确分数写进了 `Node.value`。**
但程序里确实存在一个 **可能造成状态污染的点** ：空步裁剪没有使用 RAII，超时时可能跳过 `undoNullMove()`。

---

## 1. 日志中的现象确实存在

运行日志第一回合里，`candidate_count` 是 44，最佳着法 `h2->i2` 的分数是 150。

但紧接着很多完全不同的走法也都是 150，例如：

```json
"move": "c3->c4", "score": 150
"move": "d0->e1", "score": 150
"move": "e0->e1", "score": 150
"move": "b2->b6", "score": 150
```

这些走法的 `source`、`target` 显然不同，但分数相同。 后面还持续出现大量 `score = 150` 的候选着法，直到 rank 33。

这个现象不是偶然，而是由当前根节点搜索写法直接导致的。

---

## 2. 主要错误在 `alpha_beta_PVS_select`

问题代码在这里：

```cpp
for(auto& Node : selected){
    searchTime.check();
    {
        MoveGuard guard(this,Node);
        int score = -alpha_beta_PVS_search(d - 1,-beta,-alpha);

        Node.value = score;
    }

    if(Node.value > alpha){
        alpha = Node.value;
    }
}
```

也就是在根节点中，每搜索一个着法，就把返回值直接写入：

```cpp
Node.value = score;
```

然后如果它比当前 `alpha` 大，就更新 `alpha`。

这在“选择最佳着法”时可以工作，但 **不能把 `Node.value` 理解成每个走法的真实评分** 。因为后面的走法是在已经提高过的 `alpha` 窗口下搜索的。一旦某个走法不能超过当前最优分，它往往只会返回一个边界值，而不是精确值。

举例说：

```cpp
alpha = 150;
```

后面的某个走法真实分数可能是：

```cpp
80
-20
120
149
```

但因为它们都不能超过 150，搜索可能都返回 `150` 这个边界值。于是日志里就会看到大量不同走法都是 150。

所以错误不是“这些走法真的一样好”，而是：**程序把 fail-low / fail-high 的边界返回值当成了精确评分保存到了 `MoveNode.value`。**

---

## 3. `alpha_beta_PVS_search` 本身就是 fail-hard 返回边界值

你的搜索函数在 beta 截断时直接返回：

```cpp
return beta;
```

在搜索结束时返回：

```cpp
return alpha;
```

代码位置如下：beta 截断发生时写入置换表并返回 `beta`。 如果没有 beta 截断，最后写入置换表并返回 `alpha`。

这就是典型的  **fail-hard Alpha-Beta** 。它返回的很多值只是“这个节点至少 / 至多到某个边界”，不是精确局面分。

你还在置换表探测里进一步把边界压成当前窗口边界：

```cpp
if(entry.flag == ALPHA && entry.score <= alpha){
    val = alpha;
    return true;
}
if(entry.flag == BETA && entry.score >= beta){
    val = beta;
    return true;
}
```

也就是说，置换表命中 ALPHA / BETA 节点时，也会直接返回当前 `alpha` 或 `beta` 边界。

因此，大量相同分数并不能证明状态未更新。它更像是：**你把搜索边界值打印成了候选着法分数。**

---

## 4. 非吃子着法初始排序也会产生大量相同值

你的 `calcurmove()` 现在只对吃子着法给 MVV-LVA 分数，不吃子直接返回 0：

```cpp
if (target_piece == None) {
    return 0;
}
```

然后 `fill_sort_inMoveNodes()` 用这个值给所有候选着法初始排序。

这意味着在搜索前，大量非吃子走法初始值完全一样。进入根节点搜索后，又因为 `alpha` 边界被更新，大量 fail-low 着法会被压成同一个边界值。两者叠加，就会看到：

```text
大量不同 quiet move 拥有同一个 score
```

所以这不是单一的“状态没更新”，而是：

```text
非吃子初始分辨率低
+ 根节点把边界值当精确值保存
+ fail-hard PVS / Alpha-Beta 返回 alpha 或 beta
= 大量不同走法显示相同分数
```

---

## 5. 普通落子 / 回退机制看起来不是主要污染源

普通搜索落子是通过 `MoveGuard` 做 RAII 管理的：

```cpp
MoveGuard(ChessAI* a, MoveNode& n) : ai(a), node(n) {
    ai->MoveNodeFront(node);
}
~MoveGuard() {
    ai->MoveNodeBack(node);
}
```

`MoveNodeFront()` 调用 `makeMoveAssumeLegal()`，`MoveNodeBack()` 调用 `undoMove()`。

`makeMoveAssumeLegal()` 的逻辑是复制当前棋盘、`push_back` 新状态、`currTurnId++`，然后修改新状态中的 source / target。 `undoMove()` 则 `pop_back()`、`currTurnId--`、切换 `currColor` 并回退辅助数组。

所以普通着法搜索的状态管理本身没有明显“每步都污染棋盘”的迹象。

---

## 6. 但空步裁剪这里确实有状态污染风险

真正危险的是这里：

```cpp
this->MoveNodeVoid(); // 执行空步

int null_val = -alpha_beta_PVS_search(depth - 1 - R, -beta, -beta + 1);

this->board->undoNullMove(); // 撤销空步
```

如果 `alpha_beta_PVS_search()` 在空步递归内部触发 `TimeOutException`，程序会直接跳出当前函数， **不会执行 `undoNullMove()`** 。

这和普通着法不同。普通着法使用了 `MoveGuard`，异常抛出时析构函数会自动回退；但空步这里是手动 `MoveNodeVoid()` / `undoNullMove()`，中间一旦抛异常，就会留下一个没有撤销的空步。

你已经定义了 `NullMoveGuard`：

```cpp
struct NullMoveGuard{
    ChessAI* ai;
    NullMoveGuard(ChessAI* a) : ai(a) {ai->board->makeNullMove();}
    ~NullMoveGuard() {ai->board->undoMove(); }
};
```

但当前空步裁剪没有使用它。

这个地方确实可能造成 `searchBoard` 的 `currTurnId`、`currColor`、`state` 被污染。虽然本次日志中“大量同分”主要不是它造成的，但这是一个必须修的 bug。

---

# 应该怎么修

## 第一，修正空步裁剪，防止状态污染

把这段：

```cpp
this->MoveNodeVoid();

int null_val = -alpha_beta_PVS_search(depth - 1 - R, -beta, -beta + 1);

this->board->undoNullMove();

if (null_val >= beta) {
    return beta;
}
```

改成：

```cpp
{
    NullMoveGuard nullGuard(this);

    int null_val = -alpha_beta_PVS_search(depth - 1 - R, -beta, -beta + 1);

    if (null_val >= beta) {
        return beta;
    }
}
```

这样即使递归中超时抛异常，`NullMoveGuard` 的析构函数也会自动撤销空步。

---

## 第二，不要把根节点的边界值当成精确分数打印

如果你只是想选最佳着法，可以保留 Alpha-Beta 剪枝。但如果你想让日志中的 `score` 具有可解释性，就不能直接记录：

```cpp
Node.value = score;
```

因为这个 `score` 很多时候只是边界。

调试阶段建议先用全窗口搜索每个根着法：

```cpp
for(auto& Node : selected){
    searchTime.check();

    {
        MoveGuard guard(this, Node);

        int score = -alpha_beta_PVS_search(
            d - 1,
            minstateval,
            maxstateval
        );

        Node.value = score;
    }
}
```

注意：这里为了调试分数， **不要在每个根着法之间共享 `alpha`** 。这样每个 `Node.value` 才更接近“该走法自身的搜索评分”。

更严格一点，应当写成：

```cpp
int score = -alpha_beta_PVS_search(
    d - 1,
    -maxstateval,
    -minstateval
);
```

然后只在全部根着法都算完后排序。

这个版本会慢一些，但适合排查“为什么某步被选中”。等问题查清楚后，再恢复剪枝版。

---

## 第三，给日志增加“分数类型”，区分 exact / bound

如果你想保留剪枝效率，就应该在日志里标注：

```text
EXACT
FAIL_LOW_BOUND
FAIL_HIGH_BOUND
```

不要把所有 `Node.value` 都当成真实分数。

根节点可以这样改：

```cpp
int oldAlpha = alpha;

{
    MoveGuard guard(this, Node);
    int score = -alpha_beta_PVS_search(d - 1, -beta, -alpha);
    Node.value = score;
}

if(Node.value > alpha){
    alpha = Node.value;
    // 这个着法至少刷新了根节点 alpha，可信度较高
}else{
    // 这个分数只是 fail-low 边界，不是精确评分
}
```

如果仍然看到大量等于当前最佳分的走法，那是正常的：它们只是“未能证明比当前最佳更好”，不是“真的和当前最佳一样好”。

---

## 第四，给状态回退加断言，确认是否污染

可以在根节点搜索每个着法前后加：

```cpp
int oldTurnId = board->currTurnId;
colorType oldColor = board->currColor;
int oldStateSize = (int)board->state.size();
int oldPeaceSize = (int)board->continuePeaceTurn.size();
int oldEatenSize = (int)board->lastMoveEaten.size();

{
    MoveGuard guard(this, Node);
    int score = -alpha_beta_PVS_search(d - 1, -beta, -alpha);
    Node.value = score;
}

assert(board->currTurnId == oldTurnId);
assert(board->currColor == oldColor);
assert((int)board->state.size() == oldStateSize);
assert((int)board->continuePeaceTurn.size() == oldPeaceSize);
assert((int)board->lastMoveEaten.size() == oldEatenSize);
```

如果修了空步 RAII 后这些断言都不炸，那么棋盘状态基本没有被污染。

---

## 最终判断

你的程序 **不是大量普通着法都没有更新棋盘** ；普通着法的 `makeMoveAssumeLegal()` / `undoMove()` / `MoveGuard` 结构总体是能回退状态的。

真正的问题是两类：

1. **显示分数错误** ：`alpha_beta_PVS_select()` 把 Alpha-Beta / PVS 的边界返回值当作每个根着法的精确分数保存到 `Node.value`，导致大量不同着法显示相同分数。
2. **潜在状态污染** ：空步裁剪手动 `MoveNodeVoid()` 后递归搜索，如果中途超时抛异常，会跳过 `undoNullMove()`，应改成 `NullMoveGuard`。

优先修空步 RAII；然后把根节点调试搜索改成全窗口搜索，或者至少在日志里区分 exact score 和 bound score。
