
在你的程序运行日志中，发现 `select` 着法容器里存在大量“着法不同但得分相同”的 Move。出现这种情况是博弈树搜索中的常见现象，主要由 **Alpha-Beta/PVS 剪枝的窗口边界效应** 和 **静态评估粒度不够** 导致，而不一定是棋盘状态被污染。

以下是具体的分析和原因所在：

### 1. PVS（主变搜索）/ Alpha-Beta 剪枝的固有特性（主要原因）

在 `alpha_beta_PVS_select` （即根节点的搜索循环）中：

* 你的程序使用了 Alpha-Beta 剪枝的逻辑。当第一个节点（或目前最好的节点）被搜索并返回一个最高分 `alpha` 后，后续的其他 Move 在搜索时，传入的界限是 `[-beta, -alpha]`。
* 如果后续的 Move 实际上比当前的最佳着法要差（即属于劣等着法），由于发生 **Fail-Low（低出边界）**，搜索树会被快速剪枝，并向上传递一个**上限值（经常直接被处理为原 `alpha` 值或者相同的裁断评估值）**。
* 这导致根节点中所有**没有比当前最佳着法更好**的 Move，因为没有做全窗口搜索，其返回的具体分值并没有真实计算出来（被剪枝了），最终被赋了完全一样的分值（通常等于此层的 `alpha` 值）。

### 2. 叶子节点的静态评估值冗余 (Quiescence Search 退化)

当你搜索抵达最大深度后（`depth == 0`），程序调用了 `quiescence_search`。

* 如果这些不同的棋步都属于“不吃子”的静态棋步（Quiet Moves），就会直接终止于叶子节点的静态评估函数 `calstaticstate`。
* 由于你在静态评估里使用的是子力价值 + **位置价值表（Piece-Square Table）**。如果多个不同的走法（比如同一个车平移到同一横线的不同位置，或者无进攻机会的兵移动），所在位置的预设评估分（如 `mid_Rook` 或 `mid_KingPawn_no_attack`）是相等的，没有额外的动态因子加成，就会得到完全相同的局面评估分。

### 3. 是否存在棋盘被污染或未更新？

**程序结构保证了棋盘基本不会被污染：**
观察你在 `Chess::makeMoveAssumeLegal` 和 `Chess::undoMove` 中的设计：

```cpp
vector<Grid> copyState = state[currTurnId];
state.push_back(copyState); // 深拷贝当前棋盘状态
currTurnId++;
// ... 在新的一层修改 ...
```

```cpp
// undoMove 还原
state.pop_back(); 
currTurnId--;
```

你使用了 `vector<vector<Grid>> state` 用作类似 **系统栈深拷贝** 的操作，每一回合都完整克隆了盘面。

* **好处**：这种方式天然免疫状态被污染。只要 `undoMove()` 正常执行，`pop_back()` 会连根抛弃掉下一层的垃圾数据，**绝不会发生旧状态未还原的情况**。
* **代价**：深拷贝开销过大，非常影响搜索深度和节点展开数。这反过来验证了：由于深拷贝导致每秒能搜的节点数极少，真正的搜索深度（尤其是加上迭代加深后）非常浅，大量的并列情况暴露了出来。
