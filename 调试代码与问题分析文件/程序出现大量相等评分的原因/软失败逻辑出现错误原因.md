你的代码依然存在大量的“着法不同但得分相同”的现象，主要原因在于：**你在静态搜索（Quiescence Search）中的处理逻辑不完整，特别是你在遇到 Beta 剪枝时，错误地返回了 `beta`，导致静态搜索阶段仍旧是一个“硬失败”（Fail-Hard）过程。**

当主搜索过程深入到底层节点时，会调用静态搜索。如果静态搜索返回的是一个硬截断的值（`beta`），这个被污染的 `beta` 就会沿着递归栈一路向上传递，最终表现为你在这份对局日志中看到的那些奇怪的同分现象（比如成群结队的 17 分、262 分）。

此外，你的 `PVS_search` 中仍有一些细节会导致置换表的数据被错误评估。

以下是修复建议和深度剖析。

---

### 1. 静态搜索 (Quiescence Search) 依然是 Fail-Hard

请查看你的 `quiescence_search` 代码：

**C++**

```
        // ... (在遍历各种吃子/应将着法)
        int val;
        {
            MoveGuard guard(this, qsNodes[i]);
            // 静态搜索，传 mdepth-1 防止深度过深崩溃
            val = -quiescence_search(-beta, -alpha, mdepth - 1); 
        }
      
        // Beta 剪枝
        if (val >= beta) {
            return beta;  // 【错误点】：这里你又回到了 Fail-Hard！
        }
        // Alpha 更新
        if (val > alpha) {
            alpha = val;
        }
    }

    return alpha; // 【错误点】：如果所有着法都 fail-low，这里返回了 alpha
```

**问题分析：**

静态搜索是主搜索的延伸。如果在静态搜索中你坚持使用 Fail-Hard（返回 `beta` 或 `alpha`），那么当这个值传回给 `alpha_beta_PVS_search` 时，`PVS_search` 拿到的依然是一个“被削平”的虚假边界值，而不是真实的评估值。

**修复方案：**

让 `quiescence_search` 也彻底变成 Fail-Soft。

**C++**

```
int ChessAI::quiescence_search(int alpha, int beta, int mdepth) {
    searchTime.check();

    // 深度保护
    if (mdepth <= 0) {
        return evaluator.calstate(board->state[board->currTurnId], board->currColor);
    }
  
    // ... 前面的应将检查保持不变 ...

    // 这里的 stand 就是当前局面的基准分。如果不在被将军状态，至少你能拿到这个分数
    int stand = minstateval; 
    if (!inCheck) {
        stand = evaluator.calstate(board->state[board->currTurnId], board->currColor);
        if (stand >= beta) {
            return stand; // 【修改 1】：返回 stand 而不是 beta
        }
        if (stand > alpha) {
            alpha = stand;
        }
    }

    // ... 生成着法并过滤吃子/应将着法 ...
  
    if (inCheck && tmpMoves.empty()) {
        return minstateval + 1000; 
    }

    // ... 将节点存入 qsNodes ...

    // 【修改 2】：引入 best_val，对于非应将状态，最差我也能拿到 stand 分
    int best_val = inCheck ? minstateval : stand;

    for (int i = 0; i < qsCount; ++i) {
        // ... 你的选择排序逻辑保持不变 ...

        int val;
        {
            MoveGuard guard(this, qsNodes[i]);
            val = -quiescence_search(-beta, -alpha, mdepth - 1); 
        }
      
        // 【修改 3】：实时更新 best_val
        if (val > best_val) {
            best_val = val;
        }

        if (val >= beta) {
            return best_val; // 【修改 4】：返回真实截断值 best_val，而不是 beta
        }

        if (val > alpha) {
            alpha = val;
        }
    }

    // 【修改 5】：返回探索到的最高分
    return best_val; 
}
```

### 2. 置换表 (TT) 读取逻辑未适配 Fail-Soft

在你的 `alpha_beta_PVS_search` 中，如果命中置换表，你是这么处理的：

**C++**

```
    if(probeHash(curkey,depth,alpha,beta,TT_val,best_TT_Move)){
        return TT_val; 
    }
```

而在你的 `probeHash` 中：

**C++**

```
            if(entry.flag == ALPHA && entry.score <= alpha){
                val = alpha;     // 【错误点】：你把置换表中实际算出的 score 丢弃了，替换成了传入的 alpha！
                return true;   
            }
            if(entry.flag == BETA && entry.score >= beta){
                val = beta;      // 【错误点】：同上，你丢弃了真实 score，换成了传入的 beta！
                return true;  
            }
```

**问题分析：**

既然你已经花大力气把程序改造成了 Fail-Soft（存入 TT 的 `score` 是真实的越界分数），但在读取 TT 时，你却又手动把这些分数“截断”成了 `alpha` 和 `beta`。这等同于在读取阶段又强制执行了一次 Fail-Hard！

**修复方案：**

让 `probeHash` 也遵循 Fail-Soft 逻辑，直接返回置换表里存储的真实分数。

**C++**

```
bool probeHash(uint64_t key,int depth,int alpha,int beta,int &val,Move& bestMove){
    TTStateNode& entry = HashTable[key & (TT_SIZE - 1)];

    if(entry.zobrist_key == key){ 
        bestMove = entry.best_move;
      
        if(entry.depth >= depth){
            if(entry.flag == EXACT){
                val = entry.score;
                return true;
            }
            if(entry.flag == ALPHA && entry.score <= alpha){
                val = entry.score; // 【修改】：返回真实的 score，而不是 alpha
                return true;   
            }
            if(entry.flag == BETA && entry.score >= beta){
                val = entry.score; // 【修改】：返回真实的 score，而不是 beta
                return true;   
            }
        }
    }
    return false;
}
```

**C++**

        }

### 总结：为什么还有那么多相同分数？

只要你在递归树的 **任何一个环节** （比如静态搜索、置换表读取、空步裁剪）写了一句 `return beta;` 或者 `return alpha;`，这个“硬边界值”就会像病毒一样向上传染。

1. 根节点问子节点 A：“你最高能拿几分？”
2. 子节点 A 问孙节点，孙节点触发了你没改干净的 `return beta;`（也就是它上层传下来的边界）。
3. 这个边界值被原封不动地交回给根节点。
4. 随后去问子节点 B、C、D，只要它们同样触发了劣败或截断，它们返回的也全是这个一模一样的边界值。

请严格检查以上提到的 3 个地方，将它们全部改为 **返回真实的变量（`stand`, `best_val`, `entry.score`, `null_val`）** 。修改后，根节点就能看到每个着法真正的高低差距了。
